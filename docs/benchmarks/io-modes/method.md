# 测试方法

源码：`crates/store/benches/io_modes.rs`（`harness = false` 的手写 `main`）。

## 为什么不用 criterion

设计文档 §7.3 定的是「以**确定性计数**为主、墙钟为辅」。计数来自本文件自己的
`IoLog`，criterion 的统计功利用不上，而它会拖一整套依赖进来。所以 `Cargo.toml` 里
是 `harness = false`，不引 criterion。

同理，bench 目标是**独立编译的 crate**，以普通依赖身份链接 `rstore-store`，
看不到 `#[cfg(test)] mod testutil`——那里的 `RecordingDisk` 在这里根本不存在，
所以计数盘在 bench 文件里重写了一份。

## 夹具

```
ErasureSet::with_modes(disks, parity, modes)
```

- 几何固定为 **6 块盘 / 奇偶 2**（`data_shards = 4`），盘是 `tempfile::TempDir`
  下的真文件系统目录；
- 每块盘包一层 `CountingDisk`，它是 `LocalDisk` 的**纯转发**包装，只在
  `read_exact_at` / `stat` / `list_dir` 三个方法上做一次原子自增，不改任何行为；
- 两个模式各建一个独立的 set（各自的 `TempDir`、各自的 `IoLog`），数据分别种一遍。

## 插桩：数到的是什么

`IoLog` 四个计数器，全部是**磁盘 API 的调用次数/字节数**，不是"逻辑 IO 次数"：

| 计数 | 加在哪里 | 含义 |
|---|---|---|
| `reads` | `read_exact_at` | 真正发生的读调用数 |
| `read_bytes` | `read_exact_at` 的 `len` 参数 | **请求**的字节数，不是实际 IO 的字节数 |
| `stats` | `stat` | 元数据探测次数 |
| `lists` | `list_dir` | 目录遍历次数 |

另有一个不属于 IO 的计数：`ErasureSet::take_scratch_allocs()`，记录
**分片缓冲被显式扩容的次数**。只有 L4 用它——`pooled_write_buffers` 不减少任何一次
IO，IO 计数对它必然相同，所以必须换一个可观测的量来证明它生效。

每个工作负载开跑前 `log.reset()` 并 `take_scratch_allocs()` 归零，于是
「快照差」就是这次工作负载的开销。

## 工作负载与对照位

四个负载各配一个阴性对照。对照位是这套基准的核心：**没有对照位，
「新模式更快」就只是数字，不是证据。**

| 负载 | 主测 | 阴性对照 | 对照要证明什么 |
|---|---|---|---|
| **L1** 范围读 | 64 MiB 对象上 `GET bytes=0-99` | 同一个对象的**完整 GET** | 能省的只有范围读；整读本来就无可省 |
| **L2** 元数据缓存 | 同一个 key 上 2000 次 HEAD | 100 个**不同** key 各 HEAD 一次 | 键不同则缓存必然未命中，新模式不该更快 |
| **L3** 有界列举 | 600 key 的桶里凑满一页 100 条 | `max-keys` 大到**必须扫全** | 早停的收益只在"不用扫全"时存在 |
| **L4** 写侧缓冲 | 4 次 16 MiB 的 PUT | 4 次 **512 KiB** 的 PUT | 那 16 倍来自**跨块**复用，不是全局分配路径变了 |

L4 的对照位**必须是 512 KiB**，不能是「小于一个块就行」：≤ 128 KiB 的对象走内联分支
（`should_inline`），数据进 `meta.xl`、根本不产生分片文件，两边 `allocs` 都是 0——
那也是「相同」，但是空洞的相同。要一个**真的**单块对象，得落在
`(128 KiB, BLOCK_SIZE]` 区间里。

## 热身轮与重复轮

`measure`（`benches/io_modes.rs:206`）对每个 `(模式, 工作负载)`：

1. **先跑一轮热身并丢掉**，用的是轮次下标 `REPEAT`，与计数的 `0..REPEAT` 不重叠。
   没有这一步，第一次调用与后续调用本来就不同：`metadata_cache` 的**第一次**必然
   未命中——它要多做一轮 `list_dir` + `read_meta`，第二次起直接命中。这不是脏计数，
   是「冷启动 vs 稳态」，而断言分不出这两者。**热身之后量的是稳态。**
2. 再跑 `REPEAT` 轮，每轮重置计数器、重新计时，**取最小墙钟**。最小值而不是平均值：
   墙钟只会被噪声推**高**，不会被推低，所以最小值最接近真值。
3. 每轮结束时**断言**本轮的 `reads`/`stats`/`lists`/`allocs` 与第 0 轮逐项相等，
   不等就直接 panic。

因为热身轮会把 L2 的 key 灌进缓存，L2 阴性对照的 key 必须带**轮次下标**
（`d{round}-{i:06}`），否则热身那轮就把它们全塞进缓存了，对照位反而变成主测。
代价是种子数据里这批 key 有 `(REPEAT + 1) × L2_DISTINCT` 个。

写负载的 key 同样带轮次下标（`w{round}-{i:04}`）：不区分的话第 2 轮变成覆盖写，
`gc_superseded` 会多走一条删旧版本的路，计数于是与第 1 轮不同——那条「计数逐轮相同」
的断言会立刻炸，而那是**对的**，因为每轮在测不同的东西。

## 规模参数

**报告里的每个数字都必须与这些取值一起写**，否则复现不了。

| 常量 | 取值 | 说明 |
|---|---|---|
| `L1_SIZE` | 64 MiB | 只读 100 字节的那个对象有多大 |
| `L2_HEADS` | 2 000 | HEAD 密集负载的请求数；不种数据，纯请求量 |
| `L2_DISTINCT` | 100 | L2 阴性对照里不同 key 的个数（每个都要一次 PUT） |
| `L3_KEYS` | 600 | 列举负载的桶里有多少 key |
| `L3_PAGE` | 100 | 列举主测要凑满一页多少条 |
| `L4_SIZE` | 16 MiB | 写负载的对象大小 |
| `L4_ITERS` | 4 | 写负载的轮数 |
| `REPEAT` | 2 | 每个 `(模式, 工作负载)` 重复几轮 |

**规模是从「跑得完」倒推的，不是从「好看」倒推的。** 种数据要写
`(REPEAT + 1) × L2_DISTINCT + L3_KEYS + 2` 个对象 × 2 个 set，每次 PUT 都要在
6 块盘上 fsync——实测约 **33 ms/次**，这个数决定了整套基准的墙钟下限。最初的计划是
256 MiB / 10k key，光种数据就要十几分钟，所以降到现在这组数。

**这对 L3 的倍数影响最大**：桶只有 600 条而一页要 100 条，早停收益的上限本来就只有
5/6，桶越大这个机制的相对收益越明显。

## 复现

```bash
cargo bench -p rstore-store --bench io_modes
```

输出会打印规模参数、八行结果（四负载 × 两模式），最后是一段读法提示。
**每次运行的完整输出都原样存进 `raw/`**（`YYYY-MM-DD-run-X.txt`），不整理、不复述——
结论从原始输出里推，不反过来。存两次是为了拿到「跨运行计数一致」这个证据。

`main` 里另有两条硬断言，不靠眼看：

- L4 主测的 `allocs` 必须是 `L4_ITERS × 16 × 4`（旧）= 256 / `L4_ITERS × 4`（新）= 16；
- L4 单块对照两行的 `allocs` 必须相等（各 16）。

任何一条对照位的差异显著非零，**先修测量再谈结论**——那说明数据集串了，
或者计数没被重置。
